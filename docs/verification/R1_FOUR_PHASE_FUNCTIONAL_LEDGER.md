## Shipped behavior (offline; read-only records)
- R1 `forms`: `serviceAppointment.vue:10237–10280` reads `currentNode.exts.formList`; a saved node form includes `_id`, `formDefId`, `formTitle`, `state=1/-1`. On an already authorized WorkOrder detail, the read adapter retains **only** typed reference IDs, optional title and state — not the raw FormData values.
- R1 `repeat`: `serviceAppointment.vue:10284–10324` separately queries `biz/extForm/query/{formDefId}` with an R1 workflowId filter; an optional **already included** `node.formDataList` may be displayed. If the detail has no embedded `formDataList`, it is **not queried** and is **not evidence of zero records**.
- The new optional `TechnicianApiReadPort.listRepeatFormReferences` now encodes a **bounded** R1-compatible `biz/extForm/query/{formDefId}` request with `is:workflowId|string#and`, `ne:state|integer#and=-1`, `sortField=createTime`, `sortOrder=desc` and FlipPageInfo `page/rows` (backend `modulemini/biz/ExtFormController.query` delegates to `new FlipPageInfo<>(request)`). Results are stripped to safe reference fields and malformed inputs fail closed. **This port is intentionally NOT called by any main-app UI yet:** specific production/non-Mock read scope and sample identity remain on HOLD under #201. The existence of an optional read method does not authorize live queries.
- Read mapper `readR1NodeFormList` returns `undefined` if no R1 list evidence; rejects malformed or duplicate record identities; caps displayed entries at 50 and marks truncation. Unknown server status is not labeled as completed.
- The source-mapped request encoders and `executeR1Stage1FunctionalCandidate` are now connected to the strict, **synthetic DEV Mock-only** 020/021 App controller. This is not a live R1 adapter. For `forms`, the local protocol runs FormData upsert → full `workflowNode/updateExts/{runtimeNodeId}` → `workflow/process` with both form ID slots blank when saving and completing; ordinary save stops after EXTS, while later completion uses the definition ID and an authoritative non-empty forms list. Existing-row updates preserve the full source record; deletion updates EXTS and soft-deletes FormData in R1 order. For `repeat`, the App queries records within the actual workflow run, saves each record independently, uses the returned FormData IDs for completion, joins those IDs for `workflow/process`, and uses the separate remove endpoint for deletion. The Mock gateway rejects mismatched source types, actor/role, runtime node, FormDef and workflow run.
- Each Mock protocol step is preceded by a durable `may_have_dispatched` receipt and revalidates its actor/node scope. A missing/ambiguous ACK retains the receipt and blocks another submission; there is no automatic replay. Receipts close only after a separate Mock readback verifies the expected FormData and, for `forms`, the full EXTS list. For Workflow completion, the node and every referenced FormData ID must read back as complete. This is durable synthetic Mock evidence, not a server-side R1 transaction or Production/Beta parity claim.
- A closed 020/021 node shows green completion only after the controller confirms that no transaction receipt remains. A pending receipt reopens the read-only recovery/hold surface; if the receipt cannot be checked, the UI shows an unverified state instead of completion.
- The WorkOrder Detail shows `R1NodeFormsOverview` when the **selected, authorized current task** has already-read list evidence. Empty, malformed, deleted, unknown and truncated states are distinct. Only read model and display: **no Add, Delete, UpdateExts, FormData save, Workflow Process, or extra backend read is triggered by this view.**
- Existing A06-A durable write fence and A06-B special-node mutation denial remain unchanged. Normal single-record path and the DEV-only Mock-019 local preview remain independent.
- All UI text and list data are from the authorized WorkOrder detail context; no raw customer fields, phone, FormData values, cookies, or auth headers are persisted in the list projection.
