## Common permission and capability-state model

The shared application uses the following semantic states. Platform Adapters
map native/MP-specific mechanics into these states; they do not force identical
OS behavior.

| State | Meaning | Shared behavior | Native/platform responsibility |
| --- | --- | --- | --- |
| `not_requested` | The platform has not asked for capability consent yet. | Offer a purpose-specific request path. | Map MP authorization status or OS permission status. |
| `granted` | Capability is usable for the requested operation. | Proceed with the normalized operation. | Confirm current availability where the OS can revoke access. |
| `denied` | User denied the current request but may retry. | Explain purpose and offer retry where appropriate. | Handle MP/Android/iOS denial mechanics. |
| `denied_permanently_or_settings` | Further requests require system settings or cannot be re-prompted. | Offer settings recovery if supported; otherwise manual fallback. | Android permanent denial, iOS settings, or MP settings behavior. |
| `unavailable` | Device/system service or capability is unavailable. | Keep workflow usable where possible and explain limitation. | Location service off, no camera, missing calendar/provider, or device failure. |
| `unsupported_platform` | The selected platform cannot provide the capability in the current build. | Fail explicitly or hide only the conditional action. | Adapter reports capability support; no shared API guessing. |
| `cancelled` | User intentionally cancelled picker, scan, calendar, or capture. | Return to the current flow without treating it as validation failure. | Normalize platform cancellation/error codes. |
| `error_retryable` | Temporary native/network/upload failure. | Preserve safe local state and expose retry. | Include an actionable reason without leaking native objects. |

## G2 Architecture Input

- Shared Vue 3 / uni-app code remains viable for business workflows, normalized capability states, form values, and workflow commands across MP-WEIXIN, Android, and iOS.
- Explicit Platform Adapters are required for storage, one-shot location, calendar, camera/media selection, scan, phone contact, and native permission/settings mechanics.
- API/Upload Adapters own token acquisition, upload transport, backend media references, and lookup calls; Qiniu and `wx` APIs must not enter Dynamic Form Runtime.
- Dynamic Form Runtime owns only normalized media/scan values and approved widget capabilities; Workflow Runtime owns evidence gates and appointment/workflow commands.
- Android/iOS may use thin native/plus/uni bridges behind adapters for calendar, location settings, camera, and media. G1-D does not prove that a new plugin class is required.
- Background tracking, H5 parity, password persistence, clipboard shortcuts, and unselected custom widgets should not be carried forward.
- `BLOCKS_G2 = 0`. The four UNKNOWNs are G4 product/slice verification items; none changes the current shared-codebase plus explicit-adapter architecture direction.
